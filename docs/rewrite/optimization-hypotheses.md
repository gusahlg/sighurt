# Optimization hypotheses for wave 3

Measurable hypotheses proposed by the three independent reviews of wave 2 (commit bc03573), kept here as the starting list for the optimization wave. Each still needs a stated metric, a baseline measurement with bench/, and a keep-only-if-better decision. See also bench/results/IPC-REMOVAL.md (H12–H18) and bench/HYPOTHESES.md.

## From the correctness review

- WPE loop wakeups: GLib's descriptors polled by the owner loop (calloop sources) instead of the watch thread plus a ping cut the loop wakeups per animated WPE frame from 4.0 (decision 73) to 2 or fewer. Metric: wakeups ÷ page_frames_presented on the WebGL page of the engines.sh `wpe` scenario at 60 Hz, plus CPU % of the sig process. Expected: down at least 50 % in wakeups, CPU down.
- Hidden chrome surfaces: freeing the free SHM buffers of hidden targets (the standard chrome's `page` surface after leaving sig://home, the status overlay) lowers sig's PSS after 'open sig://home at 200 %, then an engine page' by 2–3 page-sized buffers (about 30 MB each at 1920×1000×2). Metric: PSS and the diagnostics' `buffer_bytes` of hidden chrome targets. Expected: down.
- WPE SHM fallback: copying only WebKit's damage rectangles instead of whole frames cuts the fallback's bytes per frame. Metric: `shm_bytes / shm_copies` on the pixman run of window-checks.sh (now 1.35 GB in 6 s at 1280×760) and the compositor's CPU %. Expected: down in proportion to the damaged area.
- Wasm frames: sending band damage (`damage_buffer`) instead of whole-surface damage for SHM frames brings sway's CPU on `wasm-raf` from 28.2 % back toward the baseline's 14.7 % (H14). Metric: compositor CPU % in bench/run. Expected: down.
- Snapshot cost: every core change (each hovered link is a StatusTextChanged) rebuilds and contains every tab's title and URL, up to 32 Ki characters each. Caching contained strings per tab, or rebuilding only what changed, makes the cost per status change independent of the tab count. Metric: time in `App::snapshot` + `ChromeEvent::Snapshot` per hover event with 50 tabs holding long URLs. Expected: down, flat in the number of tabs.
- Tab list repaints: with `tabs = "left"`, any tab's title change repaints the whole `tabs` surface; damaging only that tab's row lowers the paint time per title change. Metric: `paints_tabs` area and `max_chrome_paint_us` with 40 tabs and a page that changes its title every second. Expected: down.
- First WPE page: starting the WPE runtime, and a spare web process, at idle after launch when `[routing.wpe] hosts` is non-empty shortens navigate-to-first-frame for the first WPE page of a session. Metric: `first-frame` ms for the first WPE navigation (362 ms on River) and the extra PSS paid for it. Expected: latency down, PSS up; measure both.
- Hidden animated WPE tab: an unmapped WPE view stops WebKit's rendering and requestAnimationFrame. Metric: wakeups/s and CPU % of sig plus WebKit's web process with an animated page in a background WPE tab over 2 minutes. Expected: near idle (about 0 wakeups/s); a non-zero steady rate would show visibility isn't reaching WebKit.
- Hand-off cost: a link handed from Servo to WPE keeps the Servo view as a retained segment. Metric: PSS growth over 20 consecutive Servo→WPE hand-offs in one tab. Expected: bounded by RETAINED_VIEWS, levelling off after the first few; unbounded growth would be a lifecycle bug.

## From the security review

- WPE downloads are fetched twice: WebKit's network process starts the response, then `sig` fetches it again with reqwest, without WebKit's cookies. Letting WebKit write to a destination `sig` chooses and cleans (`webkit_download_set_destination` in `decide-destination`) should halve the bytes fetched per download (2x the file size down to 1x) and cut the time to the 'Saved' status. Measure with the test server's byte counter.
- The SHM fallback copies the whole frame on every present (`ShmBuffers::copy` copies every row and `damage` is empty when copied). Tracking each buffer's age and copying only the damaged rows should lower `shm_bytes` per frame on pixman for a small animation (a 100x100 spinner on a 1280x800 page) roughly in proportion to the damaged area (expected more than 10x).
- A page that calls `history.replaceState` with a URL near 32 KiB on every animation frame makes the chrome lay out and repaint the whole address each time. Shaping only the visible part of the address field should lower `max_chrome_paint_us` and owner-thread CPU on such a page (expected well over 5x for long URLs); the remaining question is whether paints/s stays at or below the frame rate.
- A Wasm guest calling `api_download_url` N times per `on_frame` starts N OS threads (download.rs:113). Measure thread count and RSS against N; going through the throttled download service should cap both at about 1 new download per second per tab, independent of N.
- WPE's DMA-BUF path still takes about 4.0 owner-loop wakeups per animated frame (decision 73). Waking the owner from the GLib watch thread only when the owner isn't already due for a frame callback should lower wakeups per frame in `window-checks.sh` (target 2 or fewer) with the same pacing (16.7 ms median).

## From the performance review

- H-WPE1 (process cache): with the WebKit cache model set to DOCUMENT_BROWSER (or the process cache purged when the last WPE view closes), the WPEWebProcess count reaches 0 within 2 s of closing the last WPE tab, and tree PSS falls by at least 130 MiB (397.6 → ≤265 MiB in `wpe-closed`). Guards: WPE back/forward latency (no back-forward cache) and first-frame after navigation in WPE.
- H-WPE2 (cross-engine retention): retaining at most 1 hidden view per tab for process-backed engines, or evicting views hidden for more than 60 s to Records, brings a Servo→WPE→Servo tab from 453.7 to ≤270 MiB tree PSS. Guard: going back into an evicted segment is a reported reload, with its latency measured.
- H-WPE3 (lazy WebKit load): `dlopen` of libWPEWebKit on the first WPE view lowers a Servo-only session's PSS by 25–30 MiB (at least the 7.7 MiB private dirty), cuts the ld.so relocations at launch from 82k by more than half, and lowers `startup.mapped_s` by a few ms. Guards: WPE first frame after navigation, and every `engines.sh` `wpe` check.
- H-WPE4 (no flite): building WPE WebKit with `-DENABLE_SPEECH_SYNTHESIS=OFF` lowers sig's PSS by about 10 MiB in Servo-only sessions and each WebKit process's private dirty memory by about 3.1 MiB. Guard: the WPE smoke and engine tests (only speechSynthesis is lost).
- H-WPE5 (watch thread): writing the interrupt only when the watch thread is polling (not parked), plus skipping re-arms when nothing was dispatched and nothing was called into WebKit, lowers sighurt-wpe-glib's context switches on `wpe-anim` from about 5.0 to ≤3.5 per frame and sig's process wakeups from about 813 to ≤720/s. Guards: frame rate ≥58/s at 60 Hz, idle owner wakeups ≤0.2/s, the `glib_loop` unit test.
- H-WPE6 (hidden WPE tabs quiet): once the source of the 10 Hz timed waits is found (`SkiaGPUWorker` threads; not removed by WEBKIT_SKIA_GPU_PAINTING_THREADS) and stopped or suspended while the view is unmapped, tree wakeups with a hidden previously animated WPE tab fall from about 122/s to ≤5/s. Guard: time to the first frame when the tab is shown again.
- H-WPE7 (benchmark coverage): with WPE variants of `article`, `css-animation`, `many-tabs` and `tab-churn` added to bench/workloads.toml and run with the default build, expect: on `css-animation`, tree wakeups ≥3× Servo's (here 2,357 against 634/s) at CPU ≤ Servo's (15.9 against 20.5 %); on `many-tabs`, about +70 MiB PSS per extra WPE tab against about +10 MiB for Servo; on `tab-churn` with WPE tabs, ≥130 MiB retained unless H-WPE1 lands.
- H-WPE8 (JSC GC helpers): limiting the web process's GC marker threads through JSC options in the environment, which the web processes inherit, lowers WPEWebProcess wakeups on `wpe-anim` by ≥20 % (HeapHelper threads measured 23–742/s). Guards: frame rate, GC pause outliers in present timing.
- H-SRV1 (lazy Servo): starting Servo on first use when the session needs none (decision 26's logger handled by a forwarding logger) lowers PSS by 19–23 MiB and sig's thread count by 24 in WPE-only or Wasm-only sessions (home: 96.5 → 77.0 MiB), and lowers launch → first WPE frame by about 9 ms. Guard: a Servo script-thread panic still reaches Servo's handler.
- H-UI1 (hidden chrome page surface): releasing the buffers of an unlisted chrome surface lowers sig's PSS after leaving sig://home by one page-sized buffer (13.6 MiB at 2560×1600 at scale 2; 3.5 MiB at 1280×800). Guard: time from `tab.new` to home shown (one allocation and one paint).
- H-UI2 (first chrome frame at the right size): not painting before the first configure's size is known brings startup chrome paints from 6 to 3 and `discarded` from 3 to 0 on `home` (today every surface has permits=2, presented=1, discarded=1), and lowers `startup.mapped_s` by about the time of one page-sized paint.
- H-OWN1 (allocation-free frame path): with counter accessors instead of building diagnostics per frame, no `to_owned` in `Diagnostics::readbacks`, and reused Vecs in `registry.due`, `placement()` and per-pump events, steady-state heap allocations per presented frame on the owner thread fall to ~0 (heaptrack), and owner CPU per frame falls measurably on `css-animation` and `wpe-anim`.
