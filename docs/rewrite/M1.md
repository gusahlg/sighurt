# M1: mixed rendering in one Wayland window

The proof for §23 M1 of [`sighurt-rewrite-plan.md`](../../sighurt-rewrite-plan.md): a CPU chrome
strip and a real Servo 0.5 WebView in one Wayland window, the page presented by the GPU straight
into a host-owned subsurface. The experiment is `experiments/m1-mixed` (binary `m1-mixed`). It
is a prototype: no tabs, no configuration, no engine trait. This page records what works on which
system, what was measured, the exact protocol sequences that work with Servo 0.5 and surfman
0.13, and the limitations. The Wayland host (M3) and the Servo adapter (M4) build on it.

**Verdict: every M1 pass criterion holds**, on the user's system (River 0.4.8 with gharial,
NVIDIA RTX 3070, driver 595.99.02), in headless sway 1.12 on the same GPU (sway's GLES2 renderer
on NVIDIA GBM), and in headless sway with Mesa's llvmpipe as the diagnosed software path. The
headless runs pass on `louise-pc` too (RTX 4060, driver 595.80, runs N1–N4), and the checks
were repeated there after the review fixes (runs R1–R7, which `headless-checks.sh` now judges
itself).

**Which logs exist.** The logs of L1, L2, G1–G3, H1, H2, A1 and C1 were kept in a session
scratchpad on tmpfs and were lost when this machine rebooted; their numbers on this page were
transcribed from them at the time, and an independent review re-read and confirmed them before
the reboot, but they can no longer be checked. The live River runs (L1, L2) are the only evidence
for the River criterion and can be repeated only with the user's permission. The logs that
exist are in [`m1-runs/`](m1-runs/): N1–N4 (`louise-pc`, before the review fixes) and R1–R7
(`louise-pc`, after them), with two screenshots of R1.

## What was built

`experiments/m1-mixed/src/`:

| File | What it does |
|---|---|
| `main.rs` | Options, the calloop loop (no timeout: it sleeps until an event), the report, then the teardown |
| `host.rs` | The window: surface graph, the layout transaction, hide/show, input and focus routing, chrome and page presentation scheduling. SCTK for the registry, xdg-shell, seat, keyboard (xkbcommon), pointer and shm |
| `page.rs` | Servo: `PageContext` (a `RenderingContext` wrapping Servo's `WindowRenderingContext` that counts readbacks), `FrameDriver` (Servo's `RefreshDriver`, driven by frame callbacks), the waker, the delegate, input conversion, and the ordered shutdown |
| `pacing.rs` | `FramePacer`: one page frame in flight at a time; hiding gives up on the callback in flight |
| `shm.rs` | `ShmBuffers`: fixed-count XRGB8888 buffers reused only after `wl_buffer.release`, with size generations; a new size waits while more than one generation's worth of old buffers await release |
| `chrome.rs` | The strip: tiny-skia rectangles and cosmic-text text, swizzled into XRGB8888 |
| `egl.rs` | `eglSwapInterval`, `eglQueryString` and `eglTerminate` through the libEGL surfman loaded |
| `stats.rs` | Counters and timings for the report, bounded however long the run: counters, the last 8 192 durations of each kind, and only the idle window's wakeups |
| `bin/m1-pointer.rs` | A virtual pointer for the headless checks (below) |

`pages/` has the test pages; `pages/report.js` logs what the page receives with `console.log`,
which `m1-mixed` prints as `page console: …`, so input routing and page metrics are checked from
the log. `headless-checks.sh` drives input, scale and resizes inside `tools/headless-sway`, then
checks the log: it prints PASS or FAIL for each of 17 checks and exits with the number of
failures. `live-check.sh` runs once on the real desktop without injecting input.

```sh
SIG_WHAT="servo build (m1)" tools/cargo build -p m1-mixed
# Headless: input, focus, hide/show, scale changes (fractional or --integer-scale), resizes, idle.
# sway refuses the proprietary NVIDIA driver unless SWAY_UNSUPPORTED_GPU is set.
SWAY_UNSUPPORTED_GPU=true tools/heavy tools/headless-sway --renderer gles2 -- experiments/m1-mixed/headless-checks.sh OUT [--integer-scale] experiments/m1-mixed/pages/page.html
# Animation and WebGL with five hide/show cycles:
target/debug/m1-mixed --exit-after 20 --hide-cycles 5 experiments/m1-mixed/pages/animated.html
# Chrome only, idle:
target/debug/m1-mixed --chrome-only --exit-after 13
# The software path, explicitly: Mesa's EGL vendor and llvmpipe.
__EGL_VENDOR_LIBRARY_FILENAMES=/run/opengl-driver/share/glvnd/egl_vendor.d/50_mesa.json LIBGL_ALWAYS_SOFTWARE=1 target/debug/m1-mixed …
```

Keys: F2 hides/shows the page, Ctrl+L focuses the address field, Escape (there) returns to the
page, Ctrl+Q quits; clicking the chrome or the page focuses it. `--exit-after`, the compositor's
close and Ctrl+Q all leave the loop and run the same teardown; nothing calls `process::exit`.

## The presentation path that works

1. The host creates the root `wl_surface` (xdg_toplevel), the chrome subsurface and the page
   subsurface on its own connection, with wayland-client's `system` backend, so
   `Connection::backend().display_ptr()` and `ObjectId::as_ptr()` are libwayland's own
   `wl_display*` and `wl_surface*`. Both become raw-window-handle 0.6 Wayland handles
   (`DisplayHandle::borrow_raw`, `WindowHandle::borrow_raw`; the only `unsafe` besides `egl.rs`,
   justified by the teardown order below).
2. `WindowRenderingContext::new_with_refresh_driver(display, window, buffer_size, driver)`.
   surfman calls `eglGetPlatformDisplay(EGL_PLATFORM_WAYLAND_KHR, our wl_display)`, then
   `wl_egl_window_create(page wl_surface)` and `eglCreatePlatformWindowSurface`, and makes the
   context current. The EGL driver runs its own event queues on our connection; calloop's
   `WaylandSource` uses `prepare_read`, so events the driver reads for our queue are dispatched
   rather than left waiting.
3. **`eglSwapInterval(display, 0)`** right after, on the current context's window surface.
   surfman never sets it, and with the default of 1 Mesa's `eglSwapBuffers` waits for the frame
   callback of the previous swap, which a compositor may withhold forever from an unmapped or
   invisible surface. With 0 the swap never waits; the host paces frames itself.
4. Servo: `ServoBuilder` with an `EventLoopWaker` wrapping `sighurt_api::engine::EngineWaker`
   (its notify pings a calloop `Ping`), one `WebView` built on the context.
5. A page frame, only when the `FramePacer` has none in flight:
   `WebView::paint()` (WebRender draws into the EGL back buffer), then
   `wl_surface.frame()` on the page surface, then `RenderingContext::present()`
   (`eglSwapBuffers`, which attaches, damages and commits the page surface). The frame request
   is sent before the swap on the same connection, so the driver's commit carries it. The host
   never attaches or commits anything on the page surface.
6. Pacing: when that frame callback arrives, the pacer frees up and `FrameDriver::start_frame`
   runs the callbacks Servo registered through `RefreshDriver::observe_next_frame`, which wake
   the loop; Servo ticks its animations and reports `notify_new_frame_ready`, and the next turn
   paints. When Servo waits for a frame and nothing is in flight (an animation starting on a
   still page), the frame starts at once ("bootstrap tick"). Nothing runs on a timer: on River
   the page ran at the 120 Hz output's pace (frame-callback interval median 8 ms), in headless
   sway at its 60 Hz.

WebGL needs nothing extra: Servo's WebGL thread renders on its own surfman device on the same
EGL display (from `RenderingContext::connection`) and WebRender composites it through surface
textures, on the GPU.

### Counting readbacks

`PageContext` counts `read_to_image` calls (Servo's only CPU readback of the page, used for
screenshots), and wraps the GL that WebRender draws with (`gleam_gl_api`) in gleam's
`ProfilingGl` with a zero threshold, counting every call named `read_pixels*` or
`get_tex_image*`. Every audited run reported `read_to_image 0, GL reads 0` (R6a/b ran without
the audit and report `read_to_image 0`; R7 ended before its report). The audit times every
WebRender GL call, so `--no-gl-audit` turns it off for timing runs. It costs little: on the
RTX 4060 with `animated.html` for 20 s, the paint median was 0.69 and 0.68 ms with the audit (R5a,
R5b) and 0.63 and 0.63 ms without (R6a, R6b), about 0.05 ms or 8 %; present times were the same
(0.11 ms). The reviewer measured about 0.1 ms (7 %) on the RTX 3070. Not covered: GL calls on
Servo's WebGL thread, whose only reads serve page JavaScript (`readPixels`), which the test
pages don't call.

## The exact sequences

### Startup

1. Bind `wl_compositor` (v6), `wl_subcompositor`, `xdg_wm_base`, `wl_shm` (required), and
   `wp_viewporter` and `wp_fractional_scale_manager_v1` when present (`--integer-scale` binds
   neither). Fractional scale is used only with a viewporter.
2. Root surface → xdg_toplevel (server-side decorations requested, minimum size); root viewport;
   fractional-scale object on the root. Chrome and page subsurfaces: `set_position`,
   `set_desync`, a viewport each. Commit the root without a buffer.
3. The first configure (already acknowledged by SCTK) runs the layout transaction below; its
   root commit maps the window with the root and the chrome. The page subsurface has no buffer
   yet, so it isn't mapped.
4. After that commit: the rendering context, Servo and the WebView (26–184 ms, measured). The
   first `notify_new_frame_ready` presents the first page frame, which maps the page surface on
   its own (desynchronized).

### Layout transaction: resize and scale change

Triggered by `xdg_toplevel.configure` (SCTK acknowledges it on arrival) or
`wp_fractional_scale_v1.preferred_scale` (or, without it, `wl_surface.preferred_buffer_scale`
through SCTK). Metrics come from `sighurt_api::geometry::Metrics::new(LayoutEpoch::next(), rect,
scale)`, so buffer sizes follow the API's rounding rule. If the page's rectangle and scale are
unchanged, the root is just committed (an acknowledged configure takes a commit). Otherwise:

1. `wl_subsurface.set_sync` on the chrome and (if mapped) the page.
2. Root: with a viewport, `set_destination(w, h)` on the 1×1 buffer attached once; without, a
   full-size solid buffer at the integer scale, `set_buffer_scale(n)`, attach, damage.
3. Chrome: paint the whole strip into a free SHM buffer at the new buffer size, attach, damage,
   `set_destination` (or `set_buffer_scale`), commit: cached by the synchronized subsurface.
4. Page: `set_position` on its subsurface; `set_destination` (or `set_buffer_scale`) on the page
   surface, pending until the driver's next commit; `WebView::resize(buffer size)`, which
   resizes the EGL window (`wl_egl_window_resize`) before it returns, then
   `WebView::set_hidpi_scale_factor(scale)` (through the WebView, not the context: resizing the
   context directly makes Servo skip its viewport update); then, if the page is mapped and has
   presented before, a page frame at once (step 5 above). Its commit is cached too, and carries
   the new-size buffer with the new destination.
5. `xdg_surface.set_window_geometry(0, 0, w, h)`, root commit: root, chrome and page change in
   one step.
6. `wl_subsurface.set_desync` on both children.

The page frame in step 4 is WebRender's current scene at the new size; Servo reflows
asynchronously and its next `notify_new_frame_ready` brings the reflowed page, so a resize shows
old layout at the right size for a frame or two, never a wrongly sized buffer.

**A scale change can lay out one intermediate, wrong state.** `WebView::resize` and
`WebView::set_hidpi_scale_factor` each send the constellation their own
`ChangeViewportDetails` (servo-paint 0.5: `resize_rendering_context` → `set_rect` →
`send_window_size_message`, and `set_hidpi_scale_factor` → `send_window_size_message`), so when
script handles the first before the second arrives, the page lays out and gets a DOM `resize`
for the new buffer size at the old device pixel ratio, then again for the right one. The
independent review found it in the G1 and G2 logs after a scale-down (`resize: dpr 1.5 viewport
853x506`, then `dpr 1 viewport 1280x760`), in 2 of 11 runs with scale changes; R1–R4, with 10–13
scale changes each, did not show it: it is a race. Calling them in
the other order gives the other mixed state (old size, new ratio); Servo 0.5 has no call that
changes both in one message. Whether the intermediate layout is ever painted and presented was
not measured; no run had a protocol error from it. The transaction
took 1.4–19 ms with llvmpipe (median 3.1 ms, H1; 20–72 ms in the integer fallback, which fills a
full-window root buffer on the CPU in a debug build), 1.8–9.6 ms on NVIDIA (median 3.6 ms, G1;
3.4–36 ms in the integer fallback, G2), 2.6–3.0 ms on River/NVIDIA.

With both drivers the buffer after `wl_egl_window_resize` has the new size at the next swap. The
runs that show it are the integer fallback with an odd-size page: R2 (RTX 4060) and R4
(llvmpipe) take a 1001×661 page from scale 1 to 2 and back twice with `set_buffer_scale`; had
the driver committed the old 1001×661 buffer at scale 2, wlroots would have raised
`invalid_size`. The layouts logged `page buffer 2002x1322` and the runs ended with no protocol
error ([screenshot of R1 at that step](m1-runs/R1-odd-size-scale-2.png)). (The earlier G2 and
H2 changed scale only with a 1280×760 page, which is even either way, so they could not have
failed.)

### Hide and show

Hiding must not attach a null buffer to the page surface (that is the driver's surface, §9), so
the host hides by destroying the role object instead:

- **Hide:** move logical focus to the chrome if the page had it (Servo gets `blur`, and key-ups
  for keys it holds); `wl_subsurface.destroy()` on the page's subsurface, which unmaps the page
  surface at once and leaves its buffer state alone; give up on the frame callback in flight
  (`FramePacer::abandon`); `WebView::set_throttled(true)` (Servo stops its animations and slows
  its timers; the log shows `animating false`). No page frame is presented while hidden, and
  Servo's refresh-driver callbacks wait.
- **Show:** `wl_subcompositor.get_subsurface(page surface, root)` again (the surface keeps its
  subsurface role; only the role object is new), `set_position`, `set_desync`, root commit;
  `set_throttled(false)`; then a page frame at once, without waiting for any callback: the
  callback given up on may never come. Its commit maps the page with current content.

The callbacks given up on did arrive later (wlroots sends them once the surface is visible
again), and the pacer ignored them: 5 of 5 in each of L1, G3, N3 and A1 ("ignored frame
callbacks"). Show to committed frame at an unchanged size: 0.8–3.8 ms on River/NVIDIA,
0.3–4.6 ms in headless sway on NVIDIA, 1.2–6.2 ms with llvmpipe. Screenshots of G1 and H1 showed
the root background where the page was while hidden, and the current page after each show.

A show after the layout changed while hidden is slower, because the first frame paints the new
size: after the output went from scale 1 to 1.5 while the page was hidden, show to committed
frame took 9.0 ms (R1, RTX 4060, fractional) and 5.3 ms (R2, integer 2), against 0.38–0.60 ms for
the other shows of the same runs, and 219 ms (R3) and 97 ms (R4) with llvmpipe, against
1.5–1.9 ms. No protocol error; the page came back at 1.5 with the new viewport
([screenshot](m1-runs/R1-shown-after-hidden-scale.png)). The reviewer's probes on the RTX 3070
measured 13.7–18.5 ms, and 9–64 ms with llvmpipe.

### Teardown

`App::teardown`, after the loop, in this order (steps 1–5 are `App::release`, which `Drop` also
runs when the loop ends with an error or a panic, so no way out relies on the fields' drop order;
the root is then the last thing destroyed):

1. Release the `wl_keyboard` and `wl_pointer`.
2. Drop the WebView, then `Servo` (Servo 0.5 shuts down only in `Drop`: it tells the
   constellation to exit and spins until the constellation, WebGL and paint threads are done;
   1–52 ms here). That releases Servo's clones of the rendering context.
3. `Rc::try_unwrap` the context and drop it: surfman destroys the EGL window surface
   (`eglDestroySurface`, `wl_egl_window_destroy`) and the context. If another reference were
   left, the page surface would be left alive rather than destroyed under the driver.
4. `eglTerminate` on the display. surfman never terminates a display it didn't open, and a
   display still initialized at exit is terminated by the driver's exit handler (Mesa's
   `_eglFiniDisplay`), which would release the driver's objects on our connection (its
   registry, queues) after the connection is gone. That wasn't observed; terminating first
   avoids the question.
5. Destroy the page `wl_subsurface`, its viewport and `wl_surface`; the chrome's; the root's
   viewport and fractional-scale object; then the xdg_toplevel, xdg_surface and root surface.
6. A round trip, which would surface a protocol error (none occurred), then drop the event loop
   and the connection and return from `main`: exit code 0 in every run that closed normally.

When the loop ends with an error, `App`'s `Drop` runs steps 1–5 before the event loop and the
connection go. R7 killed the compositor under a live page: the dispatch failed with a broken
pipe, and the log shows the WebView, Servo, the GL context and EGL surface, `eglTerminate` and
then the page surfaces released in that order, and exit code 1 without a crash.

### Focus and input

The compositor's keyboard focus is on the root surface (logged as "keyboard: enter on the root
surface (the xdg_toplevel)"; subsurfaces never get it). The host keeps a logical focus, page or
chrome: the page has Servo focus when the window is activated, the page is shown and it has
logical focus; the address field likewise. A key press goes first to the browser shortcuts
(F2, Ctrl+L, Ctrl+Q, and Escape in the address field), whose releases are swallowed too, then to
the focus owner. Leaving the page sends Servo `blur` after key-ups for every key it still holds,
each with the key value its press had (a page that tracks keys by `KeyboardEvent.key` sees the
same key go up). R1–R4 check it: `x` held on the page while a click moves focus to the chrome
reaches the page as `keyup key x`, and no key-up has the value `Unidentified`.

Pointer events are routed by the surface Wayland delivered them to. A page position is
surface-local already and is converted once, by the page's `Metrics::to_buffer`, to device
pixels for Servo. H1 checked it, and G1 and G2 gave the same numbers on NVIDIA: at 100 %, a
click at window (100, 140) arrived at page surface (100, 100), went to Servo as device
(100, 100), and the page saw `clientX 100, clientY 100`; at 150 % the same logical point went to
Servo as device (150.1, 150.1) (the rounded buffer is 1280 pixels for 853 logical) and the page
again saw (100, 100); in the integer fallback at 200 %, device (200, 200) and again (100, 100).
Clicks on the chrome arrived chrome-local.

On the RTX 4060 the animated page (N3) ran like G3: 1 002 frames, paint median 0.70 ms, present
median 0.11 ms, frame-callback interval median 17 ms, 2 chrome paints, 0 readbacks, remap
1.1–2.1 ms. N1 and N2 repeated G1 and G2's input, focus, scale and resize results (the page
saw its clicks at `clientX 100, clientY 100` at 100 %, 150 % and integer 200 %), with 0 idle
wakeups and no protocol error; N4 (llvmpipe) presented 995 frames.

The first paint of a page takes 127–151 ms, while WebRender compiles its shaders; G3 took at
most 26 ms, after G1 and G2 had filled the NVIDIA driver's shader cache.

Idle: C1 (chrome only) had 4 wakeups in its 13 s (the configures, the buffer releases and the
exit timer), none in the last 10 s; L2 (a static Servo page on River/NVIDIA) had 32 in 16 s and
0 in the last 10 s; G1, G2, H1 and H2 had 0 in the 10 s before the close. Nothing in the
experiment runs on a timer except the `--exit-after` and `--hide-cycles` timers of the test runs
themselves.

An animated page costs about four loop wakeups per frame (L1: 8 255 for 2 063 frames, 4 187 of
them with a wake from Servo's waker and 2 064 with Wayland events, mostly the frame callbacks).
Each is cheap (a spin is about 0.02 ms); coalescing them is an optimization for M3/M4.

SHM: the chrome's two buffers never overflowed: at most one buffer of an old size waited for
release at once across H1's 26 layouts, and a repaint found both buffers held twice, waited for
the release and then painted (`buffer waits 2`), never overwriting a held buffer. Since the
review, `ShmBuffers` also bounds the old sizes in code (§10): a new size is refused, and the
invalidation kept, while it would leave more than one generation's worth of buffers (2 for the
chrome, 1 for the root) awaiting release. In R1–R4 at most 1 chrome and 1 root buffer of an old
size waited at once and the bound never had to refuse a size (`refused … 0 and 0 times`), so
the refusal path has run in no test; it relies on every older buffer having been superseded by
a committed newer one, which the compositor then releases.

## Limitations and open problems

- **Screenshots on River.** `grim -T` (toplevel capture through ext-foreign-toplevel-list and
  ext-image-copy-capture) fails against River 0.4.8: grim picks a 24-bit shm format and a stride
  aligned to 4 bytes (4 628 for the 1 542-pixel-wide window), which wlroots rejects
  (`wl_shm` error 1, invalid stride). gharial tiled the window at 1 542 wide and ignored the
  `--size` request, so the window couldn't be made a width that avoids it, and capturing the whole
  output would include the user's other windows. The live runs are evidenced by their logs
  (renderer, frame counts and pacing, focus, teardown). The pixels of the same GPU, driver and
  EGL path were in the G1–G3 screenshots (headless sway on the RTX 3070), which were lost with
  their logs (see "Which logs exist").
- **Resize shows old layout for a frame or two.** The transaction presents WebRender's current
  scene at the new size; the reflowed page follows when Servo has it. There is no grace period
  and no hiding of a stale page (§10's fallback). Servo 0.5 gives no way to know which frame
  reflects the new size. M4 has to decide whether that is acceptable.
- **Swap interval 0 makes the host's pacing mandatory.** eglSwapBuffers never throttles now, so
  presenting outside the pacer would render unthrottled. The `FramePacer` is the only thing that
  keeps one frame in flight.
- **surfman gaps the adapter must fill:** no swap-interval control (we call `eglSwapInterval`),
  no `eglTerminate` for a display from `from_display_handle` (we call it). Both go through
  `egl.rs`, which dlopens the libEGL surfman already loaded.
- **A hidden page keeps its GL context and EGL surface** (and its buffers). Fine for one view;
  the many-tab memory question (§27) is M4's.
- **Frame-callback timing is the only pacing signal**; presentation-time feedback is not used.
- **Keyboard translation is minimal** (W3C code from the evdev code, key from keysym or text);
  dead keys, AltGr and IME are M3's. With wtype in headless sway the physical codes are
  meaningless, because wtype uploads its own keymap, so the page saw `code Escape` for "x".
- **The headless checks need persistent input devices.** wtype and wlrctl add a virtual device
  per command and remove it on exit, so the seat's capabilities come and go and a client misses
  what is sent before it binds a new `wl_keyboard`/`wl_pointer`. `headless-checks.sh` keeps a
  `wtype -s 600000` running and drives the pointer with `m1-pointer`, which keeps one virtual
  pointer for the whole run. The M3 host's own input tests will need the same.
- **Not tested:** dragging between outputs with different scales, a second compositor family
  (§22), text input, clipboard, scrolling (wheel), and several views.
- **A scale change can lay out a wrong intermediate state** (new size, old device pixel ratio,
  or the reverse; see "Layout transaction"). M4 decides whether to accept one bogus layout and
  DOM `resize` per scale change, keep the page unmapped until the settled frame, or patch Servo
  to change size and ratio in one message.
- **sway sometimes drops the last resize after a storm.** In 5 of the 6 checks runs sway sent no
  configure for the `resize set 900 650` that follows the 40-size storm, so the window kept a
  storm size (580×340, 563×329, 876×608). The client laid out, acknowledged and committed every
  configure it got, and what it drew matched the last one. One suspect for the M3 host: SCTK
  acknowledges every configure on arrival, so when two arrive in one dispatch the commit carries
  only the later serial, and sway's transaction for the earlier one waits for its 200 ms timeout.
  Not investigated further.

## For integration

- CI: `experiments/m1-mixed` and `experiments/m0-coexist` link Servo, so `ci.yml`'s workspace
  clippy and test steps exclude them, like `sighurt-engine-servo` (in the working tree for the
  next commit; not an M1-owned file).
- A scale change sends Servo two viewport updates (see "Layout transaction"): M4 has to choose
  how to handle the intermediate layout.
- Adding the Wayland and text crates to a Servo build changes unified features of shared
  dependencies (the local build recompiled `servo-script` and `mozjs_sys`); expect one full Servo
  rebuild per distinct feature set.
- The host design this validates: the page target's leaf is committed only by the driver; the
  host's changes to it (viewport, buffer scale, frame request) are pending state the swap
  commits; position, stacking and mapping are the root's and the role object's. Hide by
  destroying the `wl_subsurface`; remap with a new one and present at once.
