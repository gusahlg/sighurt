# M0: Servo and Wasmtime in one process

Milestone M0 of `sighurt-rewrite-plan.md` (§23), and the second risk of §27: do Servo and
Wasmtime conflict when they are linked into one executable and initialized together? This file
records the pinned versions, the machines, the experiment and what it showed, and the review of
every piece of process-global setup the old engine processes did, with what `sig` does instead.

**Result: pass.** Servo 0.5 and Wasmtime 36 link into one executable and work together in one
process, in either initialization order: JavaScript and JavaScript Wasm in two Servo views,
Wasmtime guests in several stores trapping (out of bounds, `unreachable`) at the same time as
the pages' Wasm traps, fuel and epoch limits, a closed view, and a clean shutdown without
`process::exit`. No workaround was needed. `sig` owns the process-wide setup listed below; the
one hard limit is that Servo initializes once per process.

## The experiment

`experiments/m0-coexist` is a small program, not part of `sig`. It links Servo 0.5, Wasmtime 36
and the Wasm engine's native libraries that could clash with Servo's (FFmpeg, rodio, cpal and
ALSA, Tokio, reqwest with rustls), declared exactly as `sighurt-engine-wasm` declares them, and
exercises both engines in one process:

```sh
SIG_WHAT="servo build (m0)" tools/remote tools/cargo run -p m0-coexist   # both orders
tools/remote tools/cargo run -p m0-coexist -- servo-first               # one order
```

Without an argument it runs itself twice as a child process, once per initialization order
(`wasmtime-first`, `servo-first`): Servo initializes once per process (below), and which engine
installs its signal handlers last is the point of the two orders. The parent reports each
child's exit status, so a crash at exit counts as a failure too. Each child prints one `PASS`,
`FAIL` or `INFO` line per observation. In order:

1. **Process setup, as `sig` will do it.** The panic hook `sig` needs (below). Then rustls: with
   no provider installed, `rustls::ClientConfig::builder()` must panic (both `ring` and
   `aws-lc-rs` are enabled in this graph); then aws-lc-rs is installed.
2. **The Wasm engine's libraries.** `ffmpeg_next::init()` as `video.rs` calls it and a decoder
   lookup; a rodio source; cpal's default host and its output devices; a reqwest GET over a new
   Tokio runtime to a one-shot HTTP server on the loopback (building the client builds its
   rustls configuration from the installed provider).
3. **Wasmtime** (first, in `wasmtime-first`): an `Engine` with exactly the old `sig-wasm`
   `Config` (`consume_fuel`, Cranelift `OptLevel::Speed`), a second one that adds
   `epoch_interruption`, and two guests, each in its own `Store` with its own bounded
   `oxide.memory` (1 to 4096 pages, as `runtime.rs` instantiates them) holding its own value.
   Each guest traps out of bounds (a load just past its one page: a guard-page fault, SIGSEGV)
   and on `unreachable` (`ud2`, SIGILL), then must still hold its value. The guest module is
   in `src/guests.rs`.
4. **Servo**, built with `hard_fail: false`, a profile directory in the temp dir, and
   `setup_logging()`; two WebViews, each on its own `SoftwareRenderingContext`, load `data:`
   pages. Each page's script instantiates *the same guest module* in SpiderMonkey, with a
   `WebAssembly.Memory` as `oxide.memory`, makes it trap out of bounds and on `unreachable` 100
   times each, catching the `RuntimeError`s, and puts the counts in `document.title`, which the
   delegate reports. While the pages load, the owner thread keeps making the Wasmtime guests trap
   between Servo spins (in `wasmtime-first`). Frames are painted as the delegate asks.
5. **Wasmtime** (now, in `servo-first`), after SpiderMonkey has run: the same as step 3.
6. **The handlers.** The SIGSEGV and SIGILL dispositions are read (not changed) at the start,
   after Wasmtime's engine and after the pages ran JavaScript: each step must have replaced
   both, so the engine that came second really sits on top and chains to the other.
7. **Everything at once.** Both pages run 2000 more trap rounds each on Servo's script threads
   while a thread of our own makes a third Wasmtime guest trap in a loop, from before the
   scripts are sent until after their results arrive, and the owner thread stops both guests by
   fuel (50 M, the old per-callback limit) and a guest of the epoch engine by incrementing the
   epoch from a timer thread. The pages and the owner thread report when they ran.
8. **Panics elsewhere.** Threads named `StyleThread#m0` and `wasm-worker` panic; the hook must
   count the first as a style-thread panic, and Servo must still evaluate JavaScript.
9. **Closing a view.** View 0 is dropped; view 1 must still run its script.
10. **Shutdown, in order.** The views, then the last `Servo` handle (`Drop for ServoInner` asks
    the constellation to exit, spins until it has, then SpiderMonkey shuts down), which must
    write the profile (`cookie_jar.json`) on the way; then the Wasmtime stores and engines.
    `main` returns; nothing calls `process::exit`.
11. **A second Servo**, built in the same process after the first shut down, under
    `catch_unwind`, to record what happens.

The only `unsafe` in the experiment reads the current signal dispositions for step 6
(`sigaction` with a null new action). Nothing forces the engines to coexist.

The virtual size is address space both engines reserve for Wasm linear memories (Wasmtime
reserves 4 GiB plus guard pages per memory; SpiderMonkey does the same for its Wasm memories),
not memory in use: a limit on address space (`ulimit -v`) would break both. Resident memory
hardly falls after shutdown; jemalloc keeps freed pages for reuse, and some threads remain.

### Against the pass criteria

- **A minimal combined program links and runs correctly: pass.** Servo 0.5 and Wasmtime 36,
  with the Wasm engine's FFmpeg, audio, Tokio and reqwest dependencies, link into one
  executable from the one lockfile without a single version change, and every check passed in
  both initialization orders, including guest traps in both runtimes at the same time, several
  views and stores, and shutdown without `process::exit`. No process boundary is needed for
  coexistence.
- **No blanket unsafe workaround: pass.** The engines needed nothing: no handler juggling, no
  `unsafe impl Send`, no disabled signals-based traps, no environment tricks. The one `unsafe`
  block reads signal dispositions for the record.

The decision of §23 M0 is therefore the plan's initial one (§18, decision 1): the engines run in
`sig`'s process. What that costs, shared fate and no sandbox claim, is unchanged, and so is the
limit found in step 11: a lost Servo runtime needs a new process.

## Process-global setup

Everything below was process-wide in the old engine processes (`gpui-baseline:sighurt-engine-servo/src/{main,delegate}.rs`,
`gpui-baseline:sighurt-engine-wasm/src/main.rs`), or is process-wide inside Servo 0.5 or
Wasmtime 36 (sources in `~/.cargo/registry`). With the engines in `sig`, each item gets one
owner.

### Signal and trap handlers

- **SpiderMonkey** installs handlers for SIGSEGV and SIGILL (SIGBUS too on ARM) with
  `SA_SIGINFO | SA_NODEFER | SA_ONSTACK`, once per process, when the first `JSRuntime` is
  constructed (`js/src/vm/Runtime.cpp:157` → `wasm::EnsureEagerProcessSignalHandlers`), that is
  when the first page's script thread starts, not when Servo is built. Its handler handles a
  fault only if the faulting PC is in SpiderMonkey's Wasm code (`HandleTrap`,
  `LookupCodeBlock(pc)`); otherwise it calls the handler that was installed before it, or
  restores the default disposition so the fault is re-raised (`WasmSignalHandlers.cpp:752–797`).
- **Wasmtime** installs handlers for SIGSEGV, SIGILL and, on x86-64, SIGFPE, with the same
  flags, once per process, in the first `Engine::new` with signals-based traps (the default;
  `wasmtime/src/engine.rs:110`, `runtime/vm/sys/unix/signals.rs`). Its handler handles a fault
  only on a thread that is inside a Wasmtime call and at a PC of Wasmtime code; otherwise it
  calls the previous handler the same way (`delegate_signal_to_previous_handler`). It allocates
  a larger `sigaltstack` on each thread that enters Wasm.
- Neither removes its handlers. Wasmtime's only way to, the unsafe
  `Engine::unload_process_handlers`, aborts the process if another handler was installed after
  its own.

**Decision:** the engines install their own handlers and `sig` doesn't touch them; either
order works (steps 6–7 in both orders). Rules for `sig`: nothing else installs a handler for
SIGSEGV, SIGILL, SIGFPE or SIGBUS unless it chains to the previous one the same way; never call
`Engine::unload_process_handlers`; keep Wasmtime's signals-based traps (turning them off would
only cost speed). SpiderMonkey runs only on Servo's script and worker threads and Wasmtime only
on the threads the Wasm adapter chooses, so a thread is never inside both at once.

### Panic hook

- The old `sig-servo` hook ran the default hook, returned for panics Servo catches itself
  (`servo::should_panic_hook_suppress_termination()`, SVG rasterization), logged panics on
  other threads with `log::error!` (see Logging for why), reported a `StyleThread*` panic to the
  shell as a crashed page, and reported a main-thread panic before the process ended.
- The old `sig-wasm` hook reported a panic on its main or loader thread and called
  `process::exit(101)`.
- Servo sets no hook. Its default `Opts::hard_fail` is **true**: the constellation calls
  `process::exit(1)` on any page panic (`servo-constellation/constellation.rs:3014`).

**Decision:** `sig` installs one hook, first thing in `main`, before any engine:

1. the default hook (prints the message);
2. return if `servo::should_panic_hook_suppress_termination()`;
3. `log::error!("{info}")`: on a script thread, Servo's logger turns this into a crash page and
   `notify_crashed` for that page (`ViewFailed`); on other threads its constellation ignores
   it (no script event loop is installed there);
4. a panic on a `StyleThread*` becomes a runtime-level diagnostic of the Servo engine. It can't
   be pinned on a view: Stylo's pool is process-wide (`stylo/global_style_data.rs`,
   `STYLE_THREAD_POOL`), shared by every page.

The hook never exits the process. `sig` builds Servo with `hard_fail: false`. A panic in a Wasm
host function unwinds out of Wasmtime's `call` (Wasmtime resumes it after leaving the guest's
frames), so the Wasm adapter catches it around its guest calls and fails that view. A panic on
the owner thread anywhere else is a bug in `sig` and ends it like any Rust program. The
experiment's hook (`src/process.rs`) is this one, without the diagnostic plumbing.

### Logging

- `Servo::setup_logging()` installs the process's `log` logger: `env_logger` (filtered by
  `RUST_LOG`) together with Servo's `FromEmbedderLogger`, which forwards warnings and errors to
  the constellation (`servo/servo.rs:1057`). It calls `log::set_boxed_logger(..).expect(..)`, so
  it **panics if a `log` logger is already installed**.
- Script-thread panics reach the constellation only through that logger (an `error!` record
  while panicking becomes `LogEntry::Panic`, `servo-constellation/logging.rs:121`). Servo
  exports no other way to build it: the constellation channel is private.
- The baseline `sig` called `tracing_subscriber::fmt::init()`, which with tracing-subscriber's
  default features also installs `tracing-log`'s `LogTracer` as the `log` logger
  (`tracing-subscriber` 0.3, `src/util.rs:43`). Before Servo's `setup_logging` that makes Servo panic;
  after it, it silently fails to bridge.

**Decision:** `sig` owns the one call that installs the `log` logger, early in `main`. With the
Servo engine compiled in and enabled, that call is `Servo::setup_logging()` on the Servo
runtime, which `sig` therefore creates at startup rather than on first use (building it takes
SERVO_BUILD_MS, below); everything that logs through `log` (Servo, Wasmtime, reqwest, `sig`)
then goes through it. Without Servo, `sig` installs `env_logger` itself. If `sig`'s own code
uses `tracing`, its subscriber must not install `LogTracer`. No engine library installs a
logger.

### TLS provider

Servo's network stack builds its TLS configuration with `rustls::ClientConfig::builder()`
(`servo-net/connector.rs:393`, called when the resource thread starts,
`resource_thread.rs:223`), which takes the process-default
provider or, if none is installed, one chosen by rustls's crate features. In this graph both
`aws_lc_rs` (Servo) and `ring` (reqwest's `rustls-tls`) are enabled, so rustls can't choose and
panics (`rustls/src/crypto/mod.rs:248`); step 1 shows it. reqwest uses the process default if
there is one, else ring (`reqwest/src/async_impl/client.rs:763`).

**Decision:** `sig` installs `rustls::crypto::aws_lc_rs::default_provider()` first thing in
`main`, as the old `sig-servo` did; the Wasm engine's reqwest then uses aws-lc-rs too (step 2).

### Profile path and lock

The old `sig-servo` kept Servo's profile in `{data_dir}/sighurt/servo` (`cookie_jar.json`,
`hsts_list.json`, `auth_cache.json`, local storage) and, since every page had its own process,
took `{profile}/lock` only while Servo read the profile at startup (it waited for
`site_data()`) and again for shutdown, when Servo rewrites it; it gave up after 3 s. Servo
writes the files when its resource thread gets `Exit`, during `Drop for ServoInner`
(`servo-net/resource_thread.rs:664`).

**Decision:** one Servo runtime per `sig` process owns the profile. Several `sig` processes can
still run at once, so the runtime takes the lock before building Servo and holds it until the
last `Servo` handle has dropped (so the profile is written under it). If another `sig` holds it,
this `sig`'s Servo runs without a profile (`config_dir: None`: nothing is read or saved) and
says so in its diagnostics, instead of racing the other one's writes. The Wasm engine's
key-value store and compiled-module cache were already safe across processes.

### Environment

- Servo and Wasmtime don't change the environment, but **surfman does**, in Servo's rendering
  contexts: `create_context_descriptor`, called for every GL context (each view's, and the
  WebGL thread's), sets or removes `LIBGL_ALWAYS_SOFTWARE` and `DRI_PRIME` for the adapter it
  uses (`surfman/src/mesa_surfaceless/device.rs:56`; the Wayland and X11 devices call the
  same). A software adapter sets `LIBGL_ALWAYS_SOFTWARE=1` for the rest of the process; a
  hardware adapter removes it and, for the default "high performance" adapter, sets
  `DRI_PRIME=1` (step 4 shows the variable changing). `std::env::set_var` takes Rust's
  environment lock, but C code on other threads (Mesa, FFmpeg, glibc's own lookups) reads the
  environment without it, and adding a variable can reallocate `environ` under such a reader.
- Readers: `env_logger` (`RUST_LOG`), the Wasm engine (`SIGHURT_AOT_CACHE`), the old engines
  (`SIG_SERVO_TIMING`, `SIG_SERVO_RENDERING`).

**Decision:** `sig` reads the environment it needs at startup and never changes it after
starting threads. surfman's mutation is an upstream hazard the old `sig-servo` already had (it
ran Servo's threads too); `sig` records it as a risk rather than patching surfman (open
problem 2).

### Standard output

Both old engines duplicated file descriptor 1 for the protocol and pointed it at stderr, so a
stray `println!` in a dependency couldn't corrupt the message stream. **Dropped:** there is no
protocol, and `sig`'s stdout stays its stdout (`--help`, `--version`, `--default-config`).

| `sig-wasm`: `process::exit(1)` when the page couldn't start | The view fails |

### Global allocator

`servo-allocator` declares jemalloc the `#[global_allocator]`, so with Servo compiled in, all of
`sig` (the Wasm engine included) allocates through jemalloc; a build without Servo uses the
system allocator. `sig` must not declare an allocator of its own (two are a link error), and
M7's memory comparisons compare builds with the same allocator.

### Servo is once per process

Servo's options and preferences are process globals (`servo-config`: `OPTIONS` is a
`OnceLock`, preferences a global `RwLock`), SpiderMonkey initializes once per process
(`mozjs/src/rust.rs:204`: a second `JSEngine::init` is `AlreadyInitialized`, or
`AlreadyShutDown` after the first shut down), and the embedder's pipeline namespace is a
thread-local that may be installed once (`servo-base/id.rs:205`). Some of Servo's threads
outlive it (its `GlobalPool`, step 10) and Stylo's style-thread pool is a process-wide
`LazyLock`. A second
`ServoBuilder::build()` in the same process panics at once with "Already initialized"
(`servo-config-0.5.0/opts.rs:279`). Step 11 tried it after the first runtime shut down; while
the first is alive the same `OnceLock` fails the same way.

This is what "one runtime per engine kind" (plan §7) has to be for Servo anyway. It also means
that after `RuntimeFailed`, web pages come back only with a new process: `sig` reports it and
offers a restart (plan §14: don't promise that rebuilding the wrapper resets engine-global
state). If recovering web pages without restarting `sig` is ever required, that is the case for
a process boundary around Servo (plan §18), such as Servo's own `multiprocess` mode or a worker
running the same binary; M0 doesn't require one.

## Open problems and risks for integration

1. **A lost Servo runtime needs a new `sig` process.** Servo can't be rebuilt in the process
   (above). `ServoError::LostConnectionWithBackend` or any runtime-level failure leaves `sig`
   without web pages until it restarts; M4 reports it as `RuntimeFailed` and offers the restart.
   If that turns out to be unacceptable in daily use, a process boundary around Servo is the
   remedy (plan §18), not a second in-process runtime.
2. **surfman changes the environment from whichever thread creates a GL context**, including
   Servo's WebGL thread, while C code elsewhere may read it. Rare, and already true of the old
   `sig-servo`; a fix belongs in surfman. M1 and M4 should note which adapter the page contexts
   use (the default hardware adapter sets `DRI_PRIME=1` for the whole process).
3. **"Software" rendering isn't software on NVIDIA.** Step 4: `SoftwareRenderingContext` got
   the RTX 4060 through libglvnd. A diagnosed fallback (plan §14) must report `GL_RENDERER`,
   not the context type.
4. **Style-thread panics can't be pinned on a page** (the pool is shared), and Servo doesn't
   notice them. Keep `layout_threads = 2`, which avoided the known race; the hook reports them
   as an engine diagnostic.
5. **Shutdown can wait forever on a page.** `Drop for ServoInner` spins until the
   constellation has exited, and `JSEngineSetup` then waits for every SpiderMonkey handle
   (`servo-script/script_runtime.rs:1096`). A page that keeps Servo from exiting (a shared
   worker did, on x.com) would hang `sig`'s exit. Keep `SharedWorker` off; whether `sig` bounds
   its shutdown is its application policy (plan §20). Here, with two small pages, it took
   milliseconds.
6. **Servo is built at startup** when it is compiled in and enabled, so that its logger is the
   process's (Logging). `ServoBuilder::build` itself took about 3 ms here; the cost that
   matters, the first page's script thread, is paid on first use as before.
7. **CI:** `m0-coexist` depends on Servo, so `ci.yml`'s "workspace without Servo" jobs need
   `--exclude m0-coexist` (as they exclude `sighurt-engine-servo`), and the CLAUDE.md check
   commands likewise.
8. **The Wasm engine's compiled-module cache** is keyed by a format directory (`wasm-aot/v1`).
   Adding epoch interruption changes the compiled code, so bump it to `v2` with that change;
   otherwise every cached module fails to load once and is recompiled.
9. **Not done in this pass:** the baseline measurement of the old browser on a fixed workload
   (the first M0 item). It needs `sig`, `sig-wasm` and a full Servo build of `sig-servo` from a
   `gpui-baseline` worktree (its own lockfile) and a compositor that GPUI can present to.
